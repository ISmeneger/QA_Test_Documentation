## 1. Цель и контекст

Спланировать проверку критичных пользовательских сценариев интернет-магазина: поиск и выбор товара, просмотр данных о нём, добавление в корзину, изменение состава корзины, а также валидация форм аккаунта. Дополнительно рассмотреть REST API, задействованные в уже существующих проектах автоматизации.

Этот документ описывает **планируемое** тестирование. Он не является подтверждением выполнения проверок, соответствия сайта требованиям или наличия перечисленных ниже дефектов.

## 2. Источники информации и допущения

**Источники:** публично доступный интерфейс [American Eagle](https://www.ae.com/us/en), результаты исследования системы в личных проектах [Java](https://github.com/ISmeneger/American_Eagle_java_automation) и [Python](https://github.com/ISmeneger/American_Eagle_python_automation).

**Официальные бизнес-требования и API-контракты не предоставлены.** Поэтому ожидаемое поведение формулируется как гипотеза для последующего уточнения на основе UI, доступных описаний и наблюдений. При неоднозначности используется `Needs Clarification`; расхождение с гипотезой не автоматически считается дефектом.

Предварительные гипотезы (не утверждённые требования):

| ID | Гипотеза | Уточнение |
|---|---|---|
| `HYP-01` | Навигация ведёт в выбранный раздел каталога | Проверить соответствие заголовков и URL |
| `HYP-02` | Поиск позволяет найти соответствующий товар | Уточнить поведение при неточном/пустом запросе и рекомендации |
| `HYP-03` | Сортировка «Price: Low to High» упорядочивает отображаемые цены | Уточнить правила для sale и вариаций товара |
| `HYP-04` | Выбранные размер и товар корректно переносятся в корзину | Сверить SKU/размер/цену |
| `HYP-05` | Изменение количества обновляет итоговую сумму | Уточнить скидки, налоги, доставку и округление |
| `HYP-06` | Обязательные поля аккаунта валидируются | Уточнить правила формата, тексты ошибок и защиту от ботов |

## 3. In Scope

| Модуль | Основные проверки | Уровень риска |
|---|---|---|
| Header / Navigation | Отображение меню, переходы по категориям | Medium |
| Search | Существующий запрос, неизвестный запрос, пустой ввод | High |
| Catalog | Открытие списка, сортировка, фильтр диапазона цен | High |
| Product Details | Название, цена, варианты и размер, доступность | High |
| Shopping Bag | Добавление, изменение quantity, удаление, subtotal, несколько SKU | Critical |
| Account | Обязательные поля, валидация email, базовые отрицательные сценарии sign-in | Medium |
| API (ограниченно) | Guest token, Browse, Inventory, Bag — только разрешённые безопасные проверки | Medium |

## 4. Out of Scope

- Оплата, оформление реальных заказов, возвраты и операции с платёжными данными.
- Нагрузочное, стрессовое тестирование, сканирование безопасности и обход anti-bot-защиты.
- Массовая регистрация аккаунтов и отправка маркетинговых форм.
- Полная поддержка устройств и браузеров, полноценный аудит accessibility.
- Внутренние сервисы, недоступные спецификации и закрытые интеграции компании.

## 5. Подход и тест-дизайн

1. **Requirements review:** собрать наблюдения, гипотезы и вопросы в реестр с уникальными ID.
2. **Risk-based testing:** начать с поиска, выбора товара и корзины как ключевого пользовательского потока.
3. **Эквивалентные классы:** разделить поисковые запросы и вводимые значения на допустимые, недопустимые и пограничные группы.
4. **BVA:** проверять документированные ограничения длины, диапазонов и количества, **только после установления фактических границ**.
5. **Decision tables:** описать варианты доступности товара, выбранного размера и возможности добавления в корзину.
6. **State transitions:** проверить переходы корзины `empty → item added → quantity updated → item removed`.
7. **Exploratory testing:** фиксировать неожиданные состояния, pop-up, региональные ограничения и поведение поиска.
8. **Retest / Regression:** после выявления дефекта воспроизвести его при аналогичных условиях и проверить затронутые сценарии.

Применять проверки как вручную, так и сопоставлять их с имеющимися автоматизированными тестами. Результаты автотестов и результаты ручных проверок учитывать отдельно.

## 6. Окружение и данные

| Компонент | План / требование к фиксации |
|---|---|
| Система | Production-веб-сайт American Eagle (только безопасные сценарии) |
| Браузер | Chrome desktop; фактическую версию записать при запуске |
| ОС | Записать фактическую ОС и версию при запуске |
| Локаль/регион | Записать язык, регион, использование VPN и время теста |
| Сессия | Учитывать cookies, гостевой/авторизованный режим, открытые pop-up |
| Данные | Общедоступные товары, доступные размеры и SKU, динамические цены |
| Аккаунты | Только разрешённые личные тестовые учётные записи, если применимо |
| API | Не публиковать credentials, access token или технические секреты |

**Базовая конфигурация ещё не зафиксирована фактическим запуском.** Перед выполнением тестов создать запись об окружении.

## 7. Критерии входа (Entry Criteria)

- Сайт доступен из зафиксированного окружения.
- Согласован перечень модулей и тестируемых функций.
- Подготовлены тест-кейсы с проверяемыми ожидаемыми результатами или явно отмеченными гипотезами.
- Подготовлены допустимые тестовые данные без личной информации.
- Определён порядок фиксации статусов и дефектов.

## 8. Критерии выхода (Exit Criteria)

Для **учебного этапа документирования**:

- Созданы и рассмотрены 15–20 тест-кейсов.
- Для каждого кейса указаны связанный модуль/гипотеза, приоритет и статус.
- Подготовлена матрица покрытия, без фиктивных результатов выполнения.
- Все реально проведённые проверки имеют дату и данные об окружении.
- Для выявленных расхождений зафиксированы доказательства либо статус `Needs Clarification`.
- Подготовлен Test Summary Report с фактическими итогами и ограничениями.

Невыполненные/заблокированные проверки не объявляются успешно пройденными. Для реального релизного решения потребуются согласованные с заказчиком критерии качества, отсутствующие в данном учебном проекте.

## 9. Приоритеты и Severity

**Приоритет тестирования** задаётся по влиянию сценария на пользователя и вероятности проблемы: `Critical`, `High`, `Medium`, `Low`.

**Severity дефекта** описывает тяжесть последствий, а **Priority дефекта** — срочность исправления. Значения определяются после воспроизведения и анализа, а не автоматически по модулю.

## 10. Риски и меры

| Риск | Влияние | Меры |
|---|---|---|
| Anti-bot / Access Denied | Блокировка UI/API-сценариев | Статус `Blocked`, не обходить защиту |
| Различия региона/VPN | Иной контент, popup и ассортимент | Фиксировать регион и локаль |
| Динамические цены и остатки | Невоспроизводимость проверки | Записывать SKU, цену и время |
| Нет официальных требований | Ложная классификация дефекта | Отдельные гипотезы и `Needs Clarification` |
| Изменения production | Устаревшие тесты | Периодическое ревью сценариев |
| Ограничения доступа к аккаунту | Невозможность позитивного sign-in | Указать блокировку, не имитировать успех |

## 11. Форматы артефактов

**Test Case:** `TC-AE-XXX` — заголовок, связанная гипотеза, приоритет, предусловия, данные, шаги, ожидаемый результат, фактический результат, статус, окружение.

**Bug Report:** `BUG-AE-XXX` — заголовок, тип (`Confirmed` / `Needs Clarification` / `Demo`), окружение, шаги, expected/actual, evidence, Severity, Priority, reproducibility.

**Матрица покрытия:** `Hypothesis/Requirement ID → Test Case ID → Execution Result → Bug ID`.

**Test Summary:** дата, окружение, фактически выполненные проверки, passed/failed/blocked/not run, открытые вопросы, риски и вывод.

## 12. Предлагаемая последовательность работ

1. Подготовить `requirements/REQUIREMENTS_AND_ASSUMPTIONS.md`.
2. Составить чек-листы для Search, Catalog, Product Details, Bag, Account.
3. Оформить 15–20 проверяемых тест-кейсов.
4. Выполнить доступные безопасные проверки и задокументировать фактические результаты.
5. Подготовить только подтверждённые баг-репорты; учебные примеры явно помечать `Demo`.
6. Составить coverage matrix и test summary report.
7. Сверить ручные сценарии с Java/Python автотестами и сформировать automation backlog.
